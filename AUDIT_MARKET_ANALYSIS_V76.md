# SLOGI v76 — аудит алгоритма «Анализ доступных помещений»

Дата: 13.08.2026

## Цель

Раздел должен получать объявления коммерческой недвижимости из ЦИАН и Авито через Supabase, сохранять рынок, отслеживать изменения, определять кластер по адресу и позволять пользователю фильтровать результаты по площади, кластеру и этажу.

## Алгоритм v76

1. Пользователь задаёт критерии. Пустой критерий не ограничивает выборку.
2. `available-spaces.js` вызывает Supabase Edge Function `search-listings`.
3. Edge Function открывает страницы выдачи ЦИАН и Авито и собирает уникальные URL карточек.
4. Для каждой ссылки сначала проверяется существующий кэш `slogi_market_listings`.
   - новое объявление: повторная карточная проверка через 45 минут;
   - активное: примерно через 6 часов;
   - старше 7 дней: примерно через 12 часов;
   - снятое: не чаще суток;
   - неполная карточка без адреса/площади никогда не считается годным кэшем и перечитывается.
5. Если карточку надо читать с сайта, используется антиблокировочный каскад.
   - ЦИАН: Smart Scrape → Browserless Content → Unblock → Stealth BrowserQL + CAPTCHA solve → reader fallback.
   - Авито: Unblock → Stealth BrowserQL + CAPTCHA solve → Smart Scrape → Content → reader fallback.
   - при недоступности residential proxy по тарифу Unblock повторяется без него;
   - результат различает block / CAPTCHA / timeout / proxy-plan limitation.
6. Одновременно читается не более трёх карточек; между запросами добавлен небольшой jitter, чтобы не создавать резкие пачки запросов.
7. Из успешной страницы поля извлекаются каскадом: встроенный JSON/JSON-LD → meta/HTML → видимый текст → URL fallback для части полей Авито.
8. В Supabase выполняется upsert по `(source, listing_url)`, поэтому одна и та же карточка не создаёт дубль.
9. Изменение аренды пишется в `slogi_market_price_history`.
10. Объявление не считается снятым только потому, что исчезло из текущей выдачи. Снятие подтверждается отдельной проверкой карточки/HTTP 404-410.
11. В браузере кластеризация запускается только для строк с распознанным адресом. До трёх адресов обрабатываются параллельно, таймаут одного адреса — 9 секунд, общий лимит — около 30 секунд.
12. После кластеризации выбранные фильтры применяются к нормализованным данным, таблица сортируется и отображается.
13. Поиск всегда завершается: частичные результаты сохраняются, spinner снимается в `finally`, а источник получает понятный диагностический статус.

## Проблемы предыдущего алгоритма, исправленные в v76

- Одна заблокированная стратегия Browserless приводила к 0% распознанных карточек без реальной эскалации.
- Residential proxy использовался как безусловная зависимость; теперь ограничение тарифа определяется отдельно и есть fallback.
- Авито обрабатывался тем же способом, что ЦИАН, хотя источник блокирует обычный сценарий раньше; теперь порядок методов разный.
- При блокировке не различались CAPTCHA, timeout и обычный anti-bot block.
- Успешные карточки перечитывались слишком часто; теперь используется адаптивный кэш.
- Незавершённые карточки могли попасть в кэш и перестать исправляться; теперь неполные строки всегда перепроверяются.
- Геокодирование не должно запускаться без адреса; в v76 оно полностью пропускается для таких строк.
- Один медленный геокодер не должен блокировать весь список; добавлены параллельные батчи и таймауты.
- Диагностика была недостаточной; теперь видны методы, кэш, сетевые запросы, блокировки, CAPTCHA, таймауты и ограничение proxy-плана.
- Исчезновение из первых результатов поиска не трактуется как снятие объявления.
- Дубли предотвращаются уникальным ключом источник + URL.

## Что уже надёжно

- Клиент не обращается к ЦИАН/Авито напрямую: внешний доступ идёт через Supabase.
- История рынка отделена от списка потенциальных объектов СЛОГИ.
- Повторный скан не плодит дубли.
- Частичная недоступность одного источника не должна ломать второй.
- Кластеризация отделена от парсинга и не вызывается без адреса.
- Изменение визуальной CSS-вёрстки источника не обязательно ломает распознавание, поскольку первыми используются структурированные данные.

## Ограничения, которые остаются архитектурными

### 1. Текущий запуск не является круглосуточным мониторингом

Скан запускается кнопкой на странице. Адаптивный кэш определяет, какие карточки перечитывать чаще/реже, но сам по себе не запускает Edge Function по расписанию. Для настоящего непрерывного мониторинга нужен отдельный scheduled job/cron в Supabase.

### 2. Один интерактивный запуск не гарантирует охват абсолютно всех объявлений маркетплейса

По умолчанию v76 обходит 2 страницы и ограничивает выборку 25 URL на источник, чтобы функция укладывалась во время исполнения и не расходовала Browserless неконтролируемо. Это безопасный интерактивный режим, но не полный crawler всего рынка. Полный охват должен выполняться фоновыми порциями с сохранением cursor/page state.

### 3. Anti-bot защита остаётся внешней зависимостью

`/unblock` и `/stealth/bql` заметно повышают устойчивость, но ЦИАН/Авито могут изменять защиту. Поэтому оставлена подробная диагностика и fallback-каскад. Built-in residential proxies Browserless могут требовать платный тариф.

### 4. Поиск по кластеру выполняется после получения адреса

Кластеры СЛОГИ — собственные географические зоны, которых ЦИАН/Авито не знают. Поэтому сначала нужно получить адрес/координаты, а затем определить кластер. Это корректная архитектура, но кластер нельзя надёжно передать как серверный поисковый параметр источнику.

## Рекомендованный следующий этап для полного промышленного мониторинга

Отделить «Обновить рынок» от UI и запускать crawler по расписанию, например каждые 30–60 минут. Каждый запуск должен брать небольшой диапазон страниц каждого источника, хранить cursor, завершаться быстро и продолжать со следующего диапазона. Страница «Анализ доступных помещений» тогда будет в основном читать уже собранную базу Supabase, а не ждать обхода сайтов. Это даст реальный режим «все новые объявления», снизит таймауты интерфейса и позволит контролировать расход Browserless.
